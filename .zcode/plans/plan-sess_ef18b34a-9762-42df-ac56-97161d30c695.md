# 修复鸿蒙 HDC「总是断开 / 未检测到设备」

## 问题定性

排查已确认：

- 设备 `192.168.77.83:8710`（YH-H10S）HDC **在线**
- 页面 CDP 在设备侧 **TCP 9222**（`zhbf-fontend`），需 `hdc fport tcp:LOCAL tcp:9222`
- 设备上 **没有** Android 风格的 `@*devtools_remote*` abstract socket
- 当前链路只做 abstract 发现 + 被动扫本机 9222–9226，再被 `validDevices` 滤成空列表
- UI 因而显示「未检测到任何连接设备」（`WelcomeScreen` 在 `devicesTotal===0` 时的文案）
- 主入口是 `index.html` → `src/App.vue`（不是缺 `DeviceCard` 的 dashboard 页）

## 修复目标

1. HDC 能**主动**建立/复用 `tcp→tcp` 调试映射并发现 WebView
2. 有设备但无 target 时，UI 显示「已连接设备，未发现 WebView」，不再误报无设备
3. 兼容已有 abstract socket 路径与手动/DevEco 映射
4. **不改** workbench/CDP 协议本身；本次不做 `hdc.exe` 打包装箱（另议）

## 改动范围

### 1. `src/server/drivers/hdcDriver.js`（核心）

**A. 扩展 `parseForwards`**

同时解析：

- 现有：`tcp:LOCAL localabstract:SOCKET`
- 新增：`tcp:LOCAL tcp:REMOTE`（含 hdc 输出里带引号/制表符的形式，如 `'tcp:9222 tcp:9222'\t[Forward]`）

统一输出：

```js
{ id, localPort, socket, remotePort?, kind: 'abstract' | 'tcp' }
```

- abstract：`socket` = abstract 名（与现逻辑一致，供 `preAllocatePorts` 复用）
- tcp：`socket` = `tcp:${remotePort}`，`remotePort` 为设备端口

**B. 新增 `createTcpForward(id, localPort, remotePort)`**

```text
hdc -t <id> fport tcp:<local> tcp:<remote>
```

保留原 `createForward`（localabstract）给 abstract 路径。

**C. 重写 `probeManualForwards` → 主动发现（保持导出名以免大面积改调用）**

对每台 HDC 设备：

1. 候选设备端口：`[9222, 9223, 9224, 9225, 9226]`（与现 probe 一致）
2. 先 `fport ls`，收集已有 tcp→tcp / 本机已监听端口
3. 对每个候选 remotePort：
   - 若某本地 port 已能 `GET /json/list` 且含 page/webview → 收录
   - 否则若已有映射到该 remote → 探对应 local
   - 否则尝试建立映射：优先 `local==remote`，占用则在 9220–9399 内找空闲本地端口再 `createTcpForward`
4. `/json/list` 成功则生成与现结构一致的 `processes[]`（`processName`、`localPort`、`forwardOk`、`targets`）
5. 同一 `target.id` 多端口命中时去重，保留第一个

超时/失败保持软失败，不拖垮整次扫描。

**D. `removeAllForwards` / `removeForward`**

继续按 `tcp:<localPort>` 删除即可（hdc 对 abstract/tcp 规则都认 local 侧）；确保解析出的 tcp 条目也会被 teardown 清掉。

### 2. `src/server/deviceManager.js`

**A. HDC 手动/网络探测时机**

保持在 `processDevice` 之后调用 `probeManualForwards`，但：

- 对 **每台** HDC 在线设备调用（不要只挂 `devices[0]`），结果 `unshift` 到各自 `device.processes`
- 调用前把该设备已占用的 `localPort` 传入（可选），减少与 abstract forward 抢端口

**B. 放宽返回过滤 + 补诊断**

替换末尾「只保留有 targets 的设备」：

```js
const withTargets = devices.filter(d => d.processes?.some(p => p.targets?.length));
if (withTargets.length > 0) {
  return { ..., devices: withTargets };
}
// 有在线设备但无 WebView：原样返回，供 UI 区分
if (devices.length > 0) {
  diagnostics.messages.push({
    level: 'warn',
    message: '已检测到设备，但未发现可调试 WebView。鸿蒙请确认目标页在前台，并已开启 Web 调试（TCP 9222 或 DevEco 映射）。'
  });
}
return { ..., devices };
```

`allParsedDevices.length === 0` 时仍报 `No devices detected.`（真无设备）。

**C. 不动**

- ADB abstract 路径、`preAllocatePorts` 的 abstract 复用逻辑
- tcp 条目的 `socket` 形如 `tcp:9222`，不会误匹配 abstract entry

### 3. `src/composables/useDevices.js`（文案）

- `devices.length > 0 && targets === 0` 时增加一条非 error 提示（与后端文案互补，避免只靠 WelcomeScreen 标题）
- **仅当** `!d.devices?.length` 时才推「未检测到设备…」（已有逻辑，确认不被后端空 messages 误导即可）
- `devicesTotal` 继续用 `d.devices.length`，这样 `WelcomeScreen` 会走已有分支：「已连接设备，但未发现 debug 状态 WebView」

### 4. 测试

新增 `tests/hdc-discovery.test.mjs`（纯 Node，无框架，贴合现有 `npm test`）：

- `parseForwards`：abstract 行、tcp→tcp 行、带引号行
- 可选：对 `probeManualForwards` 用可注入的 `requestJson`/假 runHdc 做一次「已有 9222 映射 → 返回 target」的轻量测（若注入成本高，至少 lock parse 行为）

导出测试所需纯函数：在 `hdcDriver.js` 增加 `module.exports.parseForwards`（或 `_internal`），避免为测而起 Electron。

## 关键数据流（修复后）

```text
getTargets('hdc')
  → listDevices (在线)
  → discoverSockets (abstract，可能为空)
  → processDevice (abstract forwards，可能无 target)
  → probeManualForwards(deviceId)  【主动 tcp→tcp + /json/list】
  → 合并 processes
  → 有 target 则返回可调试设备；否则返回在线设备 + 明确诊断
  → useDevices / WelcomeScreen / Sidebar 正确展示
```

## 验证计划

1. `npm test`（含新测试）
2. 真机（当前 YH-H10S）：
   - 清掉多余 fport 后点刷新 → 应自动出现 `zhbf-fontend`
   - 杀掉页面/关调试 → 应显示「已连接设备，未发现 WebView」，而非「未检测到设备」
   - 拔掉/断 HDC → 「未检测到设备」
3. 回归：仅 ADB Android 设备时发现行为与改前一致
4. 开发态：`npm run build && npm start`（或现有 Electron 启动方式）看主窗口目标列表

## 实现顺序

1. `hdcDriver`：parseForwards + createTcpForward + 主动 probe
2. `deviceManager`：每设备 probe + 放宽过滤 + 诊断
3. `useDevices`：文案对齐
4. 测试 + 手动真机验证

## 风险与注意

- **自动 fport** 会在本机占用 9222+ 端口；teardown/`removeAllForwards` 需能清 tcp 规则（解析扩展后即可）
- 无线 HDC 仍可能网络抖动；本次先保证「扫得到、不误报无设备」
- 多 Web 端口设备只扫 9222–9226 常见段，与现设计一致，足够覆盖当前 bedside 场景
